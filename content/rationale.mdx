# Sueka/Social 認証・認可仕様の根拠（rationale）

- 文書種別: 設計判断・根拠記録
- 状態: 分離作業中のドラフト
- 関連文書: `spec.md`、`design.md`

本書は、規定を選んだ理由、前提、トレードオフを記録する。ここに書かれた説明だけを、実装の適合条件として扱ってはならない。適合条件は `spec.md` を参照する。

## 1. 基本方針

### 1.1 通常認証をパスキーに限定する

通常認証をパスキー（Discoverable Credentials）に限定し、ID・パスワードその他の通常認証方式を提供しない方針を採る。認証器を失った場合に備える経路はリカバリーコードで用意するが、その権限を通常セッションと同一にはしない。

### 1.2 リカバリーセッションを制限する

リカバリーコードは、認証器をすべて失った場合にもユーザーデータへのアクセスを可能にするための手段である。これを通常の認証手段と同等にすると、リカバリーコードの窃取が通常アカウントの完全な乗っ取りにつながるため、データ取得と削除申請に権限を限定する方針である。

### 1.3 主体にユーザー名・メールアドレスを持たせない

主体は UUID の ID のみを持ち、ユーザー名やメールアドレスなどの追加属性を持たない。したがって、利用者が主体 ID を記憶しているとは想定できない。リカバリーコードを使用する際には、主体 ID ではなくコードのハッシュ値を検索キーにして主体を特定する必要がある。

## 2. リカバリーコードの生成と保存

### 2.1 base32 表示

リカバリーコードは、利用者が紙などに書き留める場合があるため、表示形式として base32 を選択した。

### 2.2 高エントロピーと SHA-256

リカバリーコードは 128 ビット以上のエントロピーを持つ CSPRNG で生成する。DB のダンプが漏洩した場合にも、コード空間の総当たり探索は現実的でないという考えに基づき、保存時のハッシュには SHA-256 を選択した。

元文書では、平均探索回数を (2\^{127}) とし、Antminer S23 Hyd 3U（1160 TH/S）を 100 万台並列する仮定で、平均約 46 億 5000 万年という試算を記載していた。この試算は、ハードウェア性能と探索速度の仮定に依存する説明であり、spec の準拠条件ではない。数値を外部に提示する場合は、対象機器の性能値と計算前提を別途検証すること。

### 2.3 セッション ID のエントロピー

セッション ID は 128 ビット以上のエントロピーを持つ CSPRNG で生成する。RT の一部として署名されるため、`sid` を推測できただけでは有効な RT を偽造できない。しかし、Active 鍵の秘密鍵が漏洩している場合には、対象セッションの `sid` を含む RT を署名されることで既存セッションを奪取される可能性がある。したがって、`sid` の予測困難性は既存セッション奪取に対する防御層のひとつとなる。

## 3. トークン検証

### 3.1 署名アルゴリズムをトークンの `alg` だけで選ばない

検証アルゴリズムをトークンヘッダーの `alg` から選択すると、鍵の種類によっては Alg Confusion が成立しうる。そのため、`kid` で鍵を特定し、鍵に関連付けられたアルゴリズムとヘッダーの `alg` が一致することを確認する設計とした。

### 3.2 クロックスキューを許容しない

元文書では、認証サービスと機能サービスのシステム時刻が一致しているインフラを前提とし、期限切れトークンを許容するクロックスキューを設けない方針を採用している。分散環境では許容スキュー（例:
±30
秒）を設ける慣行もあるが、期限切れのトークンを意図的に受け入れることはリスクを伴うという判断である。この判断を維持する場合、時刻同期は運用上の前提条件となる。

### 3.3 未知の `kid` で JWKS を再取得する

未知の `kid` を受け取った際、キャッシュ状態によらず JWKS
を即時に再取得するのは、鍵ローテーション後に新しい鍵で署名されたトークンを正しく検証できるようにするためである。

## 4. 鍵ローテーション

### 4.1 平時ローテーションで旧公開鍵を残す

旧公開鍵は、有効期限内のトークンを検証するために必要となる。そのため、平時ローテーションでは旧公開鍵を即座に削除せず、RT
の有効期限、AT/RCAT の有効期限、1 分の余裕を含む期間、JWKS
で公開し続ける。

### 4.2 緊急ローテーションで Retired 鍵も削除する

Active と Retired
の鍵はいずれも同一の認証サービスプロセスのメモリ上に保持される。メモリダンプやプロセス侵害などでは、その時点でメモリ上にある複数の鍵がまとめて漏洩する可能性があるため、漏洩した鍵をひとつに限定できるとは仮定しない。そのため、緊急ローテーションでは
Retired 鍵をすべて削除する。

この選択により、旧鍵で署名された RT
は直ちに検証できなくなる。一方、旧鍵で署名された AT/RCAT は、最大 5
分の有効期限が切れるまで利用可能性が残る。

## 5. セッションとリフレッシュ

### 5.1 AT と RT の役割を分ける

AT/RCAT は認証事実を表現し、RT はリフレッシュの認可を表現する。RT の
`sub`
だけを認証済み主体の証明として扱うと、リフレッシュ対象を示す情報と認証事実が混同される。そのため、`POST /refresh`
では AT/RCAT の `sub` と RT の `sub` を照合し、認証トークンが RT
と同時またはそれ以前に発行されていることを要求する。

### 5.2 RT の再利用検知

現行 RT と使用済み RT のハッシュを保持することで、現在の RT
と一致しないトークンが、過去に使用された有効期限内の RT
かどうかを区別する。期限内の使用済み RT が再提示された場合は、RT
が複製・窃取された可能性を考慮してセッションを強制終了する。一方、すでに期限切れで記録から刈り取られた
RT は、再利用の証拠として扱わず、当該リクエストのみを拒否する。

### 5.3 `rt_spent` の期限に余裕を持たせる

使用済み RT の記録には、元の RT の `exp` より 1
分長いスコアを付与する。元の RT
の期限直前に再利用検知処理が行われたとき、照会前の刈り取りで対象記録自体が消えることを防ぐためである。KVS
の TTL
はトークンの有効期限そのものではなく、保存データを回収するための期限である。

### 5.4 並列リフレッシュの競合

同一セッションに対する並列リフレッシュでは、複数のリクエストが同じ RT
を使って状態更新を試みる可能性がある。状態更新を原子的にし、競合を検出したリクエストには
`409 Conflict` を返すことで、現行 RT と使用済み RT
の記録が不整合になることを防ぐ。

### 5.5 失効 API の冪等性

`POST /revoke` は、既に失効しているセッションや現在の RT と一致しない RT
に対しても `200 OK` を返す設計である。これは、同じ RT
を使った失効要求を複数回送信しても、クライアント側から見た結果が安定するようにするためである。監査上は、実際に削除した場合と
no-op の場合を区別する。

## 6. API の形に関する判断

### 6.1 `credential_id` を JSON ボディで渡す

パスキー失効 API では `credential_id` を URL のパスではなく JSON
ボディに含める。URL はアクセスログや `Referer`
ヘッダーなどを通じて記録される経路があるため、URL
に含める情報を抑える意図がある。

### 6.2 `POST /passkeys/revoke` を採用した理由

元文書には「DELETE にしない理由」という未解決 TODO
が残っている。理由は未決定であり、本書では補完しない。API
メソッドの選択理由を確定した後に記録する。

## 7. ブラウザー側の認証トークン保存

元文書には Session Storage、Local
Storage、またはそれに準ずる場所に保存する記述がある。メモリのみだとページ再読み込みでトークンが失われ、リフレッシュや失効が行えなくなるという理由が添えられている。ただし、この節には
TODO
が残っており、具体的な保存方式は最終決定事項として扱わない。保存方式を決定する際には、再読み込み後の利用可能性と、ブラウザー内のスクリプトからトークンにアクセスできることによるリスクの両方を判断記録に残す。

## 8. 高リスク操作に関する未決定事項

パスキー失効のような不可逆・機密性の高い操作について、通常の AT
だけで許可するか、直近の WebAuthn
アサーションによる昇格認証を要求するかは未決定である。AT/RT は
`POST /refresh` のたびに `iat` が更新されるため、現在の `iat`
だけでは「直近に認証器を実際に使用した時刻」を表現できない。要求する操作の範囲を決めた後、必要な認証強度とそれを表現するデータを設計する必要がある。

## 9. 監査ログとプライバシー

元文書は、GDPR 第 5 条 2 項（説明責任）および第 32
条（処理のセキュリティ）を根拠として監査ログを規定している。また、IP
アドレスは GDPR
上の個人データに該当し、主体を特定できない場合に限り主体の代替情報として記録する方針を示している。IP
アドレスの記録に関する法的根拠、保存期間、削除ポリシーは未規定であり、別途定める必要がある。
