### 4.1 RDB

認証主体と認証器に関する情報を保持する。

#### 主体テーブル (subjects)

*/}

| カラム   | 型      | 説明                 |
| -------- | ------- | -------------------- |
| `id`     | uuid    | 主体の ID            |
| `frozen` | boolean | 凍結されているか否か |

{/*
id: spec-subject-id-not-memorized
dependencies: [prem-uuid-not-memorized, spec-subjects-table]
*/}

主体の ID は UUID であるため、<u>ユーザーが主体の ID を記憶している</u>と想定することはできない。

{/*
id: spec-frozen-subject
dependencies: [pol-recovery-not-frozen, spec-stateless-token, spec-subjects-table]
*/}

{/* TODO: 「に対する」でよいか */}
凍結された主体に対する*アサーション結果受理* (`POST /assertion/result`) と、凍結された主体に対するログインセッションの*リフレッシュ* (`POST /refresh`) は拒否される。リカバリーセッションのリフレッシュは拒否されない。認証トークンはステートレスであるため、発行済みのものは最大 5 分間行使できる。

#### パスキーテーブル (passkeys)

{/*
id: spec-passkeys-table
*/}

| カラム          | 型          | 説明                                        |
| --------------- | ----------- | ------------------------------------------- |
| `subject_id`    |             | 主体の ID (`subjects.id` の外部キー)        |
| `credential_id` | bytea       | 認証器の Credential ID                      |
| `passkey_text`  | text        | パスキー情報 (公開鍵やカウンターなどを含む) |
| `last_used_at`  | timestamptz | 最終使用日時                                |
| `revoked_at`    | timestamptz | 失効日時 (NULL: 有効)                       |

#### リカバリーコードテーブル (recovery_codes)

{/*
id: spec-recovery-codes-table
dependencies: [pol-recovery]
*/}

| カラム       | 型          | 説明                                                 |
| ------------ | ----------- | ---------------------------------------------------- |
| `subject_id` |             | 主体の ID (`subjects.id` の外部キー)                 |
| `code_hash`  | text        | リカバリーコードの SHA-256 ハッシュ (base64, UNIQUE) |
| `used_at`    | timestamptz | 使用日時 (NULL: 未使用)                              |
| `revoked_at` | timestamptz | 失効日時 (NULL: 有効)                                |

リカバリーコードは登録時に 10 個発行される。各リカバリーコードは一度しか使用できない。

{/*

dependencies: [prin-encoding-by-path]
*/}

リカバリーコードは 128 ビット以上のエントロピーを持つ CSPRNG で生成される。表示形式は RFC 4648 の **base32** (パディングなし) を用いる。

{/*
id: spec-code-hash-lookup
dependencies: [spec-subject-id-not-memorized, spec-recovery-codes-table]
*/}

`code_hash` は一意性制約を持つ。リカバリーコードを消費する際は、`code_hash` のみを検索キーとして、レコードを特定する必要がある。

{/*
id: spec-code-hash-sha256
dependencies: [spec-recovery-code-format]
*/}

`code_hash` には SHA-256 を使用する。

### 4.2 インメモリ KVS

認証サービスの一時的な状態を管理する。次の 2 つの用途で使用する。

#### セッション管理 (`rt` / `rt_spent`)

{/*
id: spec-kvs-session-keys
*/}

| キー                   | データ型   | 説明                                                  |
| ---------------------- | ---------- | ----------------------------------------------------- |
| `rt:{sub}:{sid}`       | String     | 現在有効なリフレッシュトークンの SHA-256 ハッシュ     |
| `rt_spent:{sub}:{sid}` | Sorted Set | 使用済みリフレッシュトークンの SHA-256 ハッシュの集合 |

`{sub}` は主体の ID (大文字 hex-and-dash)、`{sid}` はセッション ID (base64url) である。

##### セッション ID

{/*
id: spec-session-id
dependencies: [prin-encoding-by-path]
*/}

セッション ID は、*アサーション結果受理* (`POST /assertion/result`) または*リカバリーコードによる認証* (`POST /recovery`) 成功時、リフレッシュトークンの一部として発行される。同一の主体が確立したセッションであっても、別々に確立されたセッションは異なるセッション ID を持つ。セッション ID はセッションを通じて一定であり、リフレッシュ時に引き継がれる。

セッション ID は 128 ビット以上のエントロピーを持つ CSPRNG で生成される。表示形式は base64url を用いる。

#### レート制限カウンター (`ratelimit:recovery`)

{/*
id: spec-ratelimit-counter
dependencies: [prem-tcp-source-not-client, spec-reverse-proxy]
*/}

| キー                      | データ型 | 説明                                                                         |
| ------------------------- | -------- | ---------------------------------------------------------------------------- |
| `ratelimit:recovery:{ip}` | String   | *リカバリーコードによる認証* (`POST /recovery`) における、時間窓内の試行回数 |

`{ip}` はクライアントの IP アドレスの正規化された文字列表現である。`{ip}` の取得元 (ヘッダー名を含む) は設定可能なパラメーターとする。

*リカバリーコードによる認証* (`POST /recovery`) の受信時、次の手順で IP アドレス単位の固定時間窓カウンターを更新する。

~~~redis
MULTI
INCR ratelimit:recovery:{ip}
EXPIRE ratelimit:recovery:{ip} <時間窓の長さ> NX
EXEC
~~~

`INCR` の結果がしきい値を超えている場合、`429 Too Many Requests` を返す。`EXPIRE` には `NX` を指定する。

しきい値および時間窓の長さは、設定可能なパラメーターとし、本書では具体的な数値を規定しない。

#### 認証条件

{/*
id: spec-auth-condition
dependencies: [pol-no-clock-skew, spec-auth-token, spec-key-slots]
*/}

認証トークンとして提示されたトークンが次の条件をすべて満たすとき、かつそのときに限り、そのトークンの `sub` で表される主体が*認証されている*と見做す:

- そのトークンが*正規の公開鍵*によって検証される
- そのトークンが*認証トークン*である (`typ` が `"at+jwt"` / `"rcat+jwt"` である)
- そのトークンが期限切れでない (`exp` が現在時刻よりも後である)
- そのトークンの `alg` が `"none"` でない
- そのトークンの `alg` が、そのトークンのヘッダーの `kid` に対応する鍵に紐づけられた署名アルゴリズムの名称と一致する

正規の公開鍵は次のものをいう:

- 認証サービスでは、*Active スロット*の鍵と、現在時刻が削除可能時刻を越えていない全ての *Retired スロット*の鍵。各鍵には、鍵の種類 (`kty`/`crv`) によらず、生成時に明示的に選択・宣言された署名アルゴリズムが紐づく ([6.1 鍵スロットの構成](#61-鍵スロットの構成) を参照)。
- 機能サービスでは、*JWKS エンドポイント*から取得した JWK またはそのキャッシュ。署名アルゴリズムは、その JWK 自身の `alg` フィールドの値とする。

トークンが正規の公開鍵によって*検証される*とは、`kid` に対応する鍵に紐づけられた署名アルゴリズムを用いて、そのトークンの署名が有効であることが確認できることをいう。このとき、検証に使用する署名アルゴリズムを、トークンのヘッダーの `alg` から選択してはならない。

{/*
id: spec-session-kind
dependencies: [pol-recovery, spec-at, spec-rcat]
*/}

機能サービスは、認証トークンの `typ` に応じて、セッション種別を区別する。

- `typ` が `"at+jwt"` の場合は通常セッションとして扱う。
- `typ` が `"rcat+jwt"` の場合はリカバリーセッションと判断し、ユーザーデータの取得と削除申請のみを許可する。

{/*
id: spec-verifier-requirements
dependencies: [spec-auth-condition, spec-jwks-endpoint]
*/}

機能サービスは、署名検証の実装にあたっては、次の要件を満たさなければならない:

- 検証に使用する鍵は、ヘッダーの `kid` と JWKS の各鍵エントリの `kid` を照合して特定する
- 未知の `kid` を含むトークンを受信した場合、キャッシュの状態によらず、JWKS エンドポイントを即時に再取得する

## 6. 鍵ローテーション

### 6.1 鍵スロットの構成

{/*
id: spec-key-slots
*/}

認証サービスはメモリ上に次の鍵を保持する:

| スロット名  | 説明                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| **Active**  | 現在トークンの署名・検証に使用している鍵。秘密鍵と公開鍵を保持する。同時に 1 組存在する。                |
| **Retired** | 過去トークンの署名に使用していた鍵。公開鍵と削除可能時刻のペアのリストを保持する。同時に複数存在しうる。 |

各鍵は、鍵の種類 (`kty`/`crv`) に加えて、その鍵とともに生成時に明示的に選択・宣言された署名アルゴリズムを保持する。署名アルゴリズムは鍵の種類から自動的に導出しない。鍵の種類と署名アルゴリズムの組は、JWKS では JWK の `kty`/`crv` と `alg` として表れる。

移行期間中は、Active・Retired の各スロットに、異なる鍵の種類 (たとえば EC と OKP) の鍵が混在しうる。


### 6.2 手順

現在各スロットにある鍵を次のように呼ぶ:

| スロット | 現在の鍵         |
| -------- | ---------------- |
| Active   | 鍵 A             |
| Retired  | 鍵 B₁, 鍵 B₂, … |

新たに投入する鍵を **鍵 X** とする。

#### 6.2.1 平時ローテーション

{/*
id: spec-rotation-routine
dependencies: [spec-key-slots, spec-jwks-endpoint]
*/}

1.  鍵 A の公開鍵と削除可能時刻のペアを Retired スロットに追加する。削除可能時刻は、*現在時刻 + リフレッシュトークンの有効期限 + 認証トークンの有効期限 + 1 分* とする。
2.  Active スロットの鍵を鍵 X で置き換える。

削除可能時刻はガベージコレクションのための値であり、鍵の失効時刻ではない。削除可能時刻を迎えるまでは鍵 A の公開鍵を JWKS のレスポンスに含め続けなければならない。

手順 1 の直後、一時的に鍵 A が Active スロットと Retired スロットの両方に存在するタイミングがあるが、JWKS エンドポイントは両スロットの公開鍵を返す。このとき、同じ鍵が重複して含まれてもよいし、重複排除されていてもよい。

#### 6.2.2 緊急ローテーション

{/*
id: spec-rotation-emergency
dependencies: [spec-stateless-token, spec-key-slots]
*/}

鍵の漏洩が疑われる場合に実行する。

1.  Retired スロットの鍵をすべて削除する。
2.  Active スロットの鍵を鍵 X で置き換える。

削除する鍵を限定したローテーション手順は規定しない。

緊急ローテーション完了後、過去に鍵 A, 鍵 B₁, 鍵 B₂, … で署名されたリフレッシュトークンは即時検証不可となる。旧鍵で署名された認証トークンは有効期限 (最大 5 分) 以内に自然失効する。

## 7. エンドポイント

### 7.1 アテステーション準備エンドポイント

{/*
id: spec-attestation-options
dependencies: [spec-webauthn]
*/}

~~~
POST /attestation/options
~~~

アテステーションを開始し、`PublicKeyCredentialCreationOptions` (CCO) を発行する。アテステーションの詳細は WebAuthn 仕様に従う。

#### リクエスト

| 場所            | 名前          | 内容                            |
| --------------- | ------------- | ------------------------------- |
| JSON コンテント | `username`    | 認証器に表示するユーザー名      |
| JSON コンテント | `displayName` | 認証器に表示する表示名 (省略可) |

#### 処理フロー

~~~mermaid
flowchart TD
    N10([POST /attestation/options 受信])
    N10 --> N20[主体の ID を生成]
    N20 --> N30[[CCO を構築]]
    N30 --> |username/displayName が空| ERR1([400 Bad Request])
    N30 --> |成功| N40[/登録状態と主体の ID をセッションストアに保存/]
    N40 --> N50{{セッション ID を Set-Cookie に付加}}
    N50 --> N60{{CCO を応答コンテントに付加}}
    N60 --> N70([200 OK])
~~~

#### レスポンス

#### 認証トークンの役割

{/*
id: spec-refresh-at-role
dependencies: [spec-refresh-semantics]
*/}

`POST /refresh` における認証トークンには、リフレッシュ対象の主体が認証済みの主体であることを確認する役割がある。

{/*
id: spec-refresh-semantics
dependencies: [spec-refresh-token]
*/}

リフレッシュとは認証済みの主体の再認証である。リフレッシュトークンは認証事実を表現しないため、リフレッシュトークンの `sub` は認証済みの主体ではなく、単にリフレッシュ対象の主体を表す。

{/*
id: spec-refresh-at-iat
dependencies: [pol-authorization-to-authenticated, spec-refresh-token]
*/}

また、認証トークンはリフレッシュトークンと同時に、あるいはより早く発行されたものである必要がある。

#### 並列リクエスト対策

{/*
id: spec-refresh-concurrency
dependencies: [spec-kvs-session-keys]
*/}

同一セッションに対する `POST /refresh` が並列に呼び出されても KVS エントリの更新が競合しないよう、`rt:{sub}:{sid}` を楽観ロックする。

~~~redis
WATCH rt:{sub}:{sid}
GET rt:{sub}:{sid}
~~~

#### 現行トークンの差し替えの原子性

{/*
id: spec-refresh-swap
dependencies: [spec-kvs-session-keys, spec-rt-current, spec-rt-spent]
*/}

現行トークンの差し替えは原子的に行う必要がある。

~~~redis
MULTI
SET rt:{sub}:{sid} <new_hash> EXAT <new_exp + 1m>
ZADD rt_spent:{sub}:{sid} <old_exp + 1m> <old_hash>
EXPIREAT rt_spent:{sub}:{sid} <old_exp + 1m>
~~~
{/* MARK: Reviewed Above */}

- `SET` と `ZADD` は原子的に行う。有効期限内のリフレッシュトークンのハッシュは、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` を合わせて、常にちょうど 1 つ保持される。
- `SET` と `EXPIREAT` は原子的に行う。`rt_spent:{sub}:{sid}` は、現行トークンが有効である間、使用済みトークンとして検出すべきリフレッシュトークンのハッシュを保持する。
- `ZADD` と `EXPIREAT` は当然原子的に行う。

#### クライアントアプリ実装上の注意

{/*
id: spec-refresh-client
dependencies: [spec-refresh]
*/}

クライアントアプリは、認証トークンの `exp` を基準に能動的なリフレッシュを試みてはならない。

クライアントアプリは、認証トークンの期限切れを示す応答を受け取った場合、`POST /refresh` の実行、およびそれが成功した場合の元の呼び出しの再試行を行うことができる。

#### レスポンス

成功時は `200 OK` を返す。`Content-Type` は `application/json` とする。提示された認証トークンと同種のトークンが返る。

~~~json
{
  "auth_token": "<認証トークン>"
}
~~~

リフレッシュトークンは `Set-Cookie` ヘッダーで返す。

### 7.7 リフレッシュトークンの失効エンドポイント

{/*
id: spec-revoke
dependencies: [spec-stateless-token, spec-refresh-token, spec-auth-token, spec-kvs-session-keys]
*/}

~~~
POST /revoke
~~~

認証トークンとリフレッシュトークンを受け取り、リフレッシュトークンに対応する KVS エントリを削除する。認証トークンはステートレスであるため、発行済みのものは最大 5 分間行使できる。

#### リクエスト

| 場所            | 名前            | 内容                      |
| --------------- | --------------- | ------------------------- |
| Cookie          | `refresh_token` | リフレッシュトークン      |
| JSON コンテント | `auth_token`    | 認証トークン (期限切れ可) |

#### 処理フロー

~~~mermaid
flowchart TD
    N10([POST /revoke 受信])
    N10 --> N20{RT の署名検証}
    N20 --> |失敗| ERR1([403 Forbidden])
    N20 --> |成功| N30[/"rt:{sub}:{sid} を取得"/]
    N30 --> N40{提示された RT のハッシュと一致するか}
    N40 --> N50{"AT/RCAT の署名検証"}
    N50 --> |失敗| ERR4([401 Unauthorized])
    N50 --> |成功| N55{typ が AT/RCAT のものか}
    N55 --> |非 AT/RCAT| ERR5([400 Bad Request])
    N55 --> |AT/RCAT| N60{sub が RT と一致するか}
    N60 --> |不一致| N70([200 OK])
    N60 --> |一致| N65{"rt:{sub}:{sid} が提示された RT のハッシュと一致していたか"}
    N65 --> |一致| N80[/"rt:{sub}:{sid} と rt_spent:{sub}:{sid} を削除"/]
    N65 --> |不一致| N85([200 OK])
    N80 --> N90([200 OK])
~~~

#### 冪等性

{/*
id: spec-revoke-idempotency
dependencies: [spec-revoke, spec-audit-events]
*/}

`rt:{sub}:{sid}` が既に削除されている場合、または提示されたリフレッシュトークンのハッシュが現在の値と一致しない場合、`403 Forbidden` ではなく `200 OK` を返す。これにより、同一のリフレッシュトークンを用いた複数回の `POST /revoke` 呼び出しは冪等となる。ただし、実際に `rt:{sub}:{sid}` を削除した場合と、削除対象が存在しなかった場合とは、監査ログ上は区別して記録する ([9.1 記録対象イベント](#91-記録対象イベント) を参照)。

#### レスポンス

成功時は `200 OK` を返す。

`Content-Type` は `application/json`、ボディは `{}` とする。AT と RT の `sub` が一致する場合、リフレッシュトークンの Cookie は `Max-Age=0` によりクライアント側でも削除する。

~~~http
Set-Cookie: refresh_token=; HttpOnly; Secure; SameSite=Strict; Max-Age=0; Path=/
~~~

AT と RT の `sub` が不一致の場合、セッションには何もせずに `200 OK` を返す。この状態では `POST /refresh` は失敗し、クライアントは RT を用いた再認証ができない。認証トークンの有効期限 (最大 5 分) が切れた時点で認証は自然に終了する。

#### 認証トークンの役割

{/*
id: spec-revoke-at-role
dependencies: [spec-refresh-at-role, spec-refresh-at-iat, pol-revoke-no-authorization]
*/}

`POST /revoke` における認証トークンには、失効対象の主体が認証済みの主体であることを確認する役割がある。

リフレッシュの場合とは異なり、リフレッシュトークン以前に発行されたことは要求しない。

### 7.8 リカバリーコードによる認証エンドポイント

#### レート制限

{/*

ブルートフォース攻撃を防ぐため、IP アドレス単位のレート制限を適用する ([4.2 インメモリ KVS](#42-インメモリ-kvs) を参照)。`recovery_code` を消費するよりも前に判定する。制限を超えた場合は `429 Too Many Requests` を返す。

| 場所            | 名前            | 内容             |

`recovery_code` を base32 として復号したとき、RFC 4648 §3.5 のパッドビットが 0 でない場合は、存在しないコードとして扱う。

#### 処理フロー

~~~mermaid

    N15 --> |超過| ERR3([429 Too Many Requests])

    N30 --> |更新 0 行| ERR2([401 Unauthorized])
    N30 --> |更新 1 行| N45[sid を生成]

    N50 --> N55[/"発行した RT のハッシュを rt:{sub}:{sid} に保存"/]
~~~

~~~sql

SET used_at = :now
WHERE code_hash = :code_hash
AND used_at IS NULL
AND revoked_at IS NULL;
~~~

## 8. セッション管理

{/*
id: spec-session-store
dependencies: [spec-kvs-session-keys]
*/}

セッションの失効とリフレッシュトークンの再利用検知を実現するために、現行トークンと使用済みトークンのハッシュをセッションストアに保持する。

### 8.1 現行トークン

{/*
id: spec-rt-current
dependencies: [spec-session-store]
*/}

キー
: `rt:{sub}:{sid}`

値
: 現在有効なリフレッシュトークンの SHA-256 ハッシュ (base64)

TTL はリフレッシュトークンの `exp` よりも 1 分長く設定する。セッションストア上の TTL はガベージコレクションのための値であり、トークンの有効期限ではない。トークンの有効期限はトークン自体の `exp` で表現されている。

### 8.2 使用済みトークン (再利用検知用)

{/*
id: spec-rt-spent
dependencies: [spec-session-store]
*/}

キー
: `rt_spent:{sub}:{sid}`

データ型
: Sorted Set

スコア
: 各リフレッシュトークンの `exp` より 1 分長い値 (NumericDate)

メンバー
: 使用済みリフレッシュトークンの SHA-256 ハッシュ (base64)

#### リフレッシュ成功時

{/*
id: spec-rt-spent-add
dependencies: [spec-rt-spent, spec-refresh-swap]
*/}

リフレッシュ成功時、古いリフレッシュトークンのハッシュをスコア付きで追加する。

~~~redis
ZADD rt_spent:{sub}:{sid} <old_rt_exp + 1m> <old_rt_hash>
~~~

Sorted Set 自体の TTL (`EXPIREAT`) は現行トークンの `exp` よりも 1 分長く設定し、トークンを差し替えるたびに更新する。現行トークンと同じく、TTL はガベージコレクションのための値である。この TTL は、Sorted Set 内の最大スコア、すなわち直近に追加したメンバー自身のスコアと常に同期させる。`EXPIREAT` は独自のマージンを持つのではなく、このスコアのマージンにそのまま追従する。

#### 再利用検知
{/* MARK: Reviewed Above */}

{/*
id: spec-reuse-detection
dependencies: [spec-rt-spent, spec-rt-current]
*/}

`POST /refresh` において、提示されたリフレッシュトークンが `rt:{sub}:{sid}` と一致しない場合、次の手順で、再利用検知を行う:

1.  スコア (元のリフレッシュトークンの `exp` + 1m) が現在時刻以前のエントリを刈り取る。

    ~~~redis
    ZREMRANGEBYSCORE rt_spent:{sub}:{sid} 0 <現在時刻>
    ~~~

2.  提示トークンのハッシュがこの Sorted Set に含まれるかどうかを調べる。

    ~~~redis
    ZSCORE rt_spent:{sub}:{sid} <presented_rt_hash>
    ~~~

3.  `ZSCORE` が値を返した場合、その RT は**有効期限内かつ使用済み**であり、再利用が検知されたことを意味する。この場合は、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` を即座に削除し、セッションを強制終了する。

    ~~~redis
    MULTI
    DEL rt:{sub}:{sid}
    DEL rt_spent:{sub}:{sid}
    EXEC
    ~~~

4.  `ZSCORE` が NULL を返した場合、その RT は「未知の RT」または「既に期限切れで刈り取られた RT」である。セッションは終了させず、当該リクエストだけを `403 Forbidden` で拒否する。

この判定順序により、**有効期限内の使用済み RT のみ**が再利用として扱われる。

## 付録 B. 根拠

### B.1 インフラ要件・データストアの根拠

#### 同一サイトに配置する理由

{/*
id: why-same-site
dependencies: [spec-same-site]
*/}

同一サイトでなければ、リフレッシュトークン (`SameSite=Strict` Cookie) が付加されず、*リフレッシュ* (`POST /refresh`) や*失効* (`POST /revoke`) が機能しなくなる。

#### `code_hash` に SHA-256 を使用する理由

{/*
id: why-code-hash-sha256
dependencies: [spec-code-hash-sha256, spec-recovery-code-format]
*/}

リカバリーコードは 128 ビット以上のエントロピーを持つため、仮に DB がダンプされたとしても、総当たり攻撃には平均 2¹²⁷ 回の試行を要する。これは現在最速の ASIC (Antminer S23 Hyd 3U; 1160 TH/S) を 100 万台並列しても、平均約 46 億 5000 万年かかる計算となる。

#### `code_hash` のみを検索キーとする理由

{/*
id: why-code-hash-lookup
dependencies: [spec-code-hash-lookup, spec-subject-id-not-memorized]
*/}

ユーザーは主体の ID を記憶していないため、リカバリーコードを消費する際に、主体の ID を入力として受け取れない。そのため、`code_hash` のみを検索キーとしてレコードを特定する必要があり、`code_hash` は一意性制約を持つ。

#### セッション ID を CSPRNG で生成する理由

{/*
id: why-session-id-csprng
dependencies: [spec-session-id]
*/}

セッション ID はリフレッシュトークンの一部として発行され、署名されているため、たとえ攻撃者がセッション ID の推測に成功したとしても、リフレッシュトークンの署名を偽装したり、`rt:{sub}:{sid}` の値を盗取し、推測したセッション ID を含む有効なリフレッシュトークンを導出したりすることは事実上不可能である。

ただし、Active スロット ([6. 鍵ローテーション](#6-鍵ローテーション)) の秘密鍵が漏洩している場合、攻撃者は、対象セッションの `sid` を計算し、その `sid` を含むリフレッシュトークンを署名することで、既存のセッションを奪取できる。よって、セッション ID の暗号学的安全性は、既存セッション奪取に対する防禦層のひとつとして機能する。

#### `EXPIRE` に `NX` を指定する理由

{/*
id: why-ratelimit-nx
dependencies: [spec-ratelimit-counter]
*/}

時間窓を固定長にするためである。

#### しきい値と時間窓を規定しない理由

{/*
id: why-ratelimit-params-configurable
dependencies: [spec-ratelimit-counter]
*/}

しきい値および時間窓の長さは、攻撃の実態に応じて運用中に調整されうる値であるためである。

#### 認証トークンをメモリに保存しない理由

メモリに保存すると、ブラウザーの再読み込みによって認証トークンが失われ、*リフレッシュ*および*失効*が行えなくなる。

{/*
id: why-alg-not-from-header
dependencies: [spec-auth-condition]
*/}

これに反すると、鍵の種類によっては Alg Confusion が成立しうる。

### B.3 鍵ローテーションの根拠

#### 削除可能時刻まで鍵 A の公開鍵を含め続ける理由

{/*
id: why-retired-key-retention
dependencies: [spec-rotation-routine]
*/}

有効期限内のトークンはすべて鍵 A で検証可能である必要があるためである。

{/* TODO: 削除可能時刻の算式 (現在時刻 + RT の有効期限 + AT の有効期限 + 1 分) の各項の根拠 */}

#### JWKS で鍵が重複してもよい理由

{/*
id: why-rotation-overlap-harmless
dependencies: [spec-rotation-routine, spec-jwks-endpoint]
*/}

手順 1 の直後には鍵 A が両スロットに存在するが、これを両スロットの公開鍵の和集合として返しても、非交和として返しても、同じ鍵が重複して含まれるだけで実害はない。したがって、JWKS エンドポイントは重複排除を行ってもよいし、行わなくてもよい。

#### 削除する鍵を限定したローテーション手順を規定しない理由

{/*
id: why-no-partial-rotation
dependencies: [spec-rotation-emergency, spec-key-slots, prem-leak-exposes-all-keys]
*/}

Active スロットと Retired スロットの鍵はいずれも、同一の認証サービスプロセスのメモリ上に保持されている ([6.1 鍵スロットの構成](#61-鍵スロットの構成)) ところ、鍵漏洩を引き起こす典型的な事象は、その時点でメモリ上に存在する鍵をまとめて暴露する。したがって、漏洩範囲が特定の 1 つの鍵に限定できるという前提を置くことはできないため、削除する鍵を限定したローテーション手順は規定しない。

### B.4 エンドポイントの根拠

#### リカバリーコードのハッシュ等を原子的に保存する理由

{/*
id: why-attestation-atomic-save
dependencies: [spec-attestation-result, pol-store-only-on-attestation-success, prem-passkey-may-be-personal-data]
*/}

保存が途中で止まり、主体のみ、または主体とパスキーのみが保存されると、アテステーションが成功していないにもかかわらず、主体とパスキーが保存された状態になる。パスキーは各国のプライバシー法上、個人情報にあたる可能性があるため、このような状態は許容しない。

#### リフレッシュに認証トークンを要する理由

{/*
id: why-refresh-requires-at
dependencies: [spec-refresh-at-role, spec-refresh, spec-refresh-semantics]
*/}

リフレッシュを行うには、リフレッシュ対象の主体が認証済みの主体であることを確認する必要がある。そこで、認証済みの主体を示すものとして、認証トークンの `sub` を用いる。

#### 監視するキーが 1 つで足りる理由

{/*
id: why-refresh-watch-single-key
dependencies: [spec-refresh-concurrency, spec-refresh-swap]
*/}

厳密には `rt_spent:{sub}:{sid}` の更新も競合しうるが、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` は原子的に更新されるため、監視するキーはいずれか 1 つで十分である。

#### 失効を冪等にする理由

*/}

`403 Forbidden` ではなく `200 OK` を返すのは、同一のリフレッシュトークンを用いた複数回の `POST /revoke` 呼び出しを冪等にするためである。

#### 失効のレスポンスを `POST /refresh` と揃える理由

{/*
id: why-revoke-response-symmetry
dependencies: [spec-revoke, spec-refresh]
*/}

`Content-Type` を `application/json`、ボディを `{}` とするのは、`POST /refresh` との対称性のためである。

#### レート制限を `recovery_code` の消費より前に判定する理由

{/*
id: why-recovery-ratelimit-first
dependencies: [spec-recovery-ratelimit]
*/}

レート制限も到達の前提の一部であるため、`recovery_code` を消費するよりも前に判定する。この判定は `recovery_code` を参照する前に行われるため、コードの存在有無について何の情報も持たない。

#### リカバリーコードの消費を単一の原子操作とする理由

{/*
id: why-recovery-atomic-consume
dependencies: [spec-recovery-consume]
*/}

`used_at` の確認と記録が原子的でないと、並列リクエストによって、同じリカバリーコードが二重に使用される可能性がある。

#### パッドビットが 0 でない入力を拒否する理由

{/*
id: why-recovery-trailing-bits
dependencies: [spec-recovery-code-trailing-bits]
*/}

パッドビットを無視して受け付けると、正規のコードを打ち損じた利用者が、そのまま通ってしまったことを観測しうる。攻撃者にとっての影響はないが、利用者の信用にかかわる。

#### `credential_id` を JSON コンテントで渡す理由

{/*
id: why-passkey-revoke-json-body
dependencies: [spec-passkey-revoke]
*/}

パスに含めた場合、アクセスログや `Referer` ヘッダーなど URL が記録される経路を通じて残りやすくなるためである。

#### 最後の 1 件のパスキーを失効させられない理由

{/*
id: why-last-passkey-protected
dependencies: [spec-passkey-revoke, spec-session-kind]
*/}

失効させると、その主体は認証手段をすべて失う。リカバリーセッションはユーザーデータの取得と削除申請のみに限定されており、通常認証の代替にはならない。

### B.5 セッション管理の根拠

#### 現行トークンの TTL を `exp` より 1 分長くする理由

{/*
id: why-rt-ttl-margin
dependencies: [spec-rt-current]
*/}

TTL が `exp` と同一の場合、`exp` 間際に試行された正当なリフレッシュが KVS エントリの消滅によって拒否されるおそれがある。

#### 使用済みトークンのスコアにマージンを持たせる理由

{/*
id: why-rt-spent-score-margin
dependencies: [spec-rt-spent, spec-rt-spent-add, spec-reuse-detection]
*/}

スコアそのものが `old_exp + 1分` というマージンを持つ理由は、再利用検知における刈り取り (`ZREMRANGEBYSCORE`) と `ZSCORE` 照会が同一リクエスト内で連続して実行されるためである。提示されたトークンの `exp` 直前に処理が行われた場合、マージンが無ければ、照会対象のメンバー自身が刈り取りによって消えてしまい、再利用が検知されない事態になる。

#### `EXPIREAT` をスコアのマージンに追従させる理由

{/*
id: why-rt-spent-expireat-sync
dependencies: [spec-rt-spent-add, why-rt-spent-score-margin]
*/}

スコアは各リフレッシュを経るごとに単調増加するため、「直近に追加したメンバーのスコア」は常に「現存する全メンバーの最大スコア」と一致し、`EXPIREAT` をそれに同期させておけば、それ以前に追加された (まだ刈り取られていない) メンバーの必要期限を下回ることはない。

#### 有効期限内の使用済み RT のみを再利用として扱う理由

{/*
id: why-reuse-detection-order
dependencies: [spec-reuse-detection]
*/}

既に `exp` を過ぎた RT は再利用ではなく単なる期限切れであり、セッション侵害の証跡には用いない。
