### 3.2 インメモリ KVS

認証サービスの一時的な状態を管理する。

{/* { "id": "spec-kvs-session-keys" } */}
#### セッション管理 (`rt` / `rt_spent`)

| キー                   | データ型   | 説明                                                  |
| ---------------------- | ---------- | ----------------------------------------------------- |
| `rt:{sub}:{sid}`       | String     | 現在有効なリフレッシュトークンの SHA-256 ハッシュ     |
| `rt_spent:{sub}:{sid}` | Sorted Set | 使用済みリフレッシュトークンの SHA-256 ハッシュの集合 |

`{sub}` は主体の ID (大文字 hex-and-dash)、`{sid}` はセッション ID (base64url) である。

{/* { "id": "spec-session-id", "dependencies": ["prin-encoding-by-use"] } */}
##### セッション ID

セッション ID は、*アサーション結果受理* (`POST /assertion/result`) 成功時、および*リカバリーコードによる認証* (`POST /recovery`) 成功時に発行され、リフレッシュトークンの一部として配信される。同一の主体が確立したセッションであっても、別々に確立されたセッションは異なるセッション ID を持つ。セッション ID はセッションを通じて一定であり、リフレッシュ時に引き継がれる。

セッション ID は 128 ビット以上のエントロピーを持つ CSPRNG で生成される。表示形式は base64url を用いる。

{/* { "id": "spec-sessions-index", "dependencies": ["spec-kvs-session-keys", "spec-session-id", "pol-recovery-not-restricted", "spec-passkeys-table"] } */}
#### セッションの索引 (`sessions`)

| キー             | データ型 | 説明                                                                                                          |
| ---------------- | -------- | ------------------------------------------------------------------------------------------------------------- |
| `sessions:{sub}` | Hash     | フィールドはセッション ID (base64url)、値はそのセッションの確立に使ったパスキーの `credential_id` (base64url) |

`{sub}` は主体の ID (大文字 hex-and-dash) である。

{/* { "id": "spec-ratelimit-counter", "dependencies": ["prem-tcp-source-not-client", "spec-reverse-proxy"] } */}
#### レート制限カウンター (`ratelimit`)

| キー                        | データ型 | 説明                                     |
| --------------------------- | -------- | ---------------------------------------- |
| `ratelimit:{ip}:{endpoint}` | String   | 固定時間窓の中でリクエストを送信した回数 |

`{ip}` はクライアントの IP アドレス (RFC 3986 Appendix A の IPv6address または IPv4address)、`{endpoint}` はエンドポイント定義 ([6. エンドポイント](#6-エンドポイント)の各節の冒頭で定義される、`METHOD /path/to/endpoint` 形式の文字列) である。クライアントの IP アドレスの取得元は設定可能とする。

#### 認証条件

認証トークンとして提示されたトークンが次の条件をすべて満たすとき、かつそのときに限り、そのトークンの `sub` で表される主体が*認証されている*と見做す。この条件を*通常の認証条件*という:

- そのトークンが*正規の公開鍵*によって検証される
- そのトークンの `alg` が `"none"` でない
- そのトークンの `alg` がそのトークンの*意図された*署名アルゴリズムの名称と一致する
- そのトークンが*認証トークン*である (`typ` が `"at+jwt"` / `"rcat+jwt"` である)
- そのトークンが期限切れでない (`exp` が現在時刻よりも後である)

*正規の公開鍵*とは次のものをいう:

- 認証サービスでは、*Active スロット*の公開鍵と、削除可能時刻を超えていない全ての *Retired スロット*の公開鍵。
- 機能サービスでは、*JWKS エンドポイント*から取得した JWK またはそのキャッシュによって表現される公開鍵。

トークンの*意図された*署名アルゴリズムとは、そのトークンの `kid` に対応する鍵に紐づけられた署名アルゴリズムであり、次のものをいう:

- 認証サービスでは、TODO
- 機能サービスでは、*JWKS エンドポイント*から取得した JWK のうち、`kid` がそのトークンの `kid` と一致するものの `alg`。

トークンが正規の公開鍵によって*検証される*とは、`kid` に対応する鍵に紐づけられた署名アルゴリズムを用いて、そのトークンの署名が有効であることが確認できることをいう。このとき、検証に使用する署名アルゴリズムを、トークンのヘッダーの `alg` から選択してはならない。

{/* { "id": "spec-session-kind", "dependencies": ["pol-recovery", "spec-at", "spec-rcat"] } */}
機能サービスは、認証トークンの `typ` に応じて、セッション種別を区別する。

- `typ` が `"at+jwt"` の場合は通常セッションとして扱う。
- `typ` が `"rcat+jwt"` の場合はリカバリーセッションと判断し、ユーザーデータの取得と削除申請のみを許可する。

{/* { "id": "spec-verifier-requirements", "dependencies": ["spec-auth-condition", "spec-jwks-endpoint"] } */}
機能サービスは、署名検証の実装にあたっては、次の要件を満たさなければならない:

- 検証に使用する鍵は、ヘッダーの `kid` と JWKS の各鍵エントリの `kid` を照合して特定する
- 未知の `kid` を含むトークンを受信した場合、キャッシュの状態によらず、JWKS エンドポイントを即時に再取得する
- JWKS のキャッシュを、`Cache-Control` の `max-age` を超えて使用しない
- JWKS を取得したときは、取得した JWK Set でキャッシュを置き換える (含まれない鍵は、キャッシュから削除する)

{/* { "id": "spec-elevated-auth", "dependencies": ["spec-auth-condition"] } */}
##### 昇格認証

認証トークンとして提示されたトークンが次の条件をすべて満たすとき、かつそのときに限り、そのトークンの `sub` で表される主体が*昇格認証されている*と見做す:

- そのトークンが*通常の認証条件*を満たす
- そのトークンの `afr` が `"authenticator"` である

{/* { "id": "spec-elevate-auth", "dependencies": ["spec-assertion-options", "spec-passkeys-revoke", "spec-sessions-revoke", "spec-sessions-revoke-all"] } */}
クライアントアプリは、昇格認証の要求を示す応答を受け取った場合、*アサーション準備* (`POST /assertion/options`) を試み、アサーションに成功した場合、元のリクエストを再試行することができる。

## 5. 鍵ローテーション

{/* { "id": "spec-key-slots" } */}
### 5.1 鍵スロットの構成

認証サービスはメモリ上に次の鍵を保持する:

| スロット名  | 説明                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| **Active**  | 現在トークンの署名・検証に使用している鍵。秘密鍵と公開鍵を保持する。同時に 1 組存在する。                |
| **Retired** | 過去トークンの署名に使用していた鍵。公開鍵と削除可能時刻のペアのリストを保持する。同時に複数存在しうる。 |

メモリ上の鍵はそれぞれ、鍵の種類 (`kty`/`crv`) に加えて、その鍵とともに生成時に明示的に選択・宣言された署名アルゴリズムを保持する。署名アルゴリズムは鍵の種類から自動的に導出しない。鍵の種類と署名アルゴリズムの組は、JWKS では JWK の `kty`/`crv` と `alg` として表れる。

移行期間中は、Active・Retired の各スロットに、異なる鍵の種類 (たとえば EC と OKP) の鍵が混在しうる。

### 5.2 手順

現在各スロットにある鍵を次のように呼ぶ:

| スロット | 現在の鍵         |
| -------- | ---------------- |
| Active   | 鍵 A             |
| Retired  | 鍵 B₁, 鍵 B₂, … |

新たに投入する鍵を **鍵 X** とする。

{/* { "id": "spec-rotation-routine", "dependencies": ["spec-key-slots", "spec-jwks-endpoint"] } */}
#### 5.2.1 平時ローテーション

1.  鍵 A の公開鍵と削除可能時刻のペアを Retired スロットに追加する。削除可能時刻は、*現在時刻 + リフレッシュトークンの有効期限 + 認証トークンの有効期限 + 1 分* とする。
2.  Active スロットの鍵を鍵 X で置き換える。

削除可能時刻はガベージコレクションのための値であり、鍵の失効時刻ではない。削除可能時刻を迎えるまでは鍵 A の公開鍵を JWKS のレスポンスに含め続けなければならない。

手順 1 の直後、一時的に鍵 A が Active スロットと Retired スロットの両方に存在するタイミングがあるが、JWKS エンドポイントは両スロットの公開鍵を返す。このとき、同じ鍵が重複して含まれてもよいし、重複排除されていてもよい。

{/* { "id": "spec-rotation-emergency", "dependencies": ["spec-stateless-token", "spec-key-slots"] } */}
#### 5.2.2 緊急ローテーション

鍵の漏洩が疑われる場合に実行する。

1.  Retired スロットの鍵をすべて削除する。
2.  Active スロットの鍵を鍵 X で置き換える。

削除する鍵を限定したローテーション手順は規定しない。

緊急ローテーション完了後、過去に鍵 A, 鍵 B₁, 鍵 B₂, … で署名されたリフレッシュトークンは即時検証不可となる。機能サービスは、JWKS のキャッシュを更新するまで、最長で JWKS のキャッシュの最大寿命に相当する期間 ([6.5 JWKS エンドポイント](#65-jwks-エンドポイント) を参照)、鍵 A, 鍵 B₁, 鍵 B₂, … で署名された認証トークンを受け入れる。

#### 認証トークンの役割

*リフレッシュ* (`POST /refresh`) における認証トークンには、リフレッシュ対象の主体が認証済みの主体であることを確認する役割がある。

{/* { "id": "spec-refresh-semantics", "dependencies": ["spec-refresh-token"] } */}
リフレッシュとは認証済みの主体の再認証である。リフレッシュトークンは認証事実を表現しないため、リフレッシュトークンの `sub` は認証済みの主体ではなく、単にリフレッシュ対象の主体を表す。

{/* { "id": "spec-refresh-at-iat", "dependencies": ["pol-authorization-to-authenticated", "spec-refresh-token"] } */}
また、認証トークンはリフレッシュトークンと同時に、あるいはより早く発行されたものである必要がある。

## 7. セッション管理

セッションの失効とリフレッシュトークンの再利用検知を実現するために、現行トークンのハッシュ、使用済みトークンのハッシュ、セッションの索引をセッションストアに保持する。

{/* { "id": "spec-rt-current", "dependencies": ["spec-refresh-token"] } */}
### 7.1 現行トークン

キー
: `rt:{sub}:{sid}`

値
: 現在有効なリフレッシュトークンの SHA-256 ハッシュ (base64)

TTL はリフレッシュトークンの `exp` よりも 1 分長く設定する。セッションストア上の TTL はガベージコレクションのための値であり、トークンの有効期限ではない。トークンの有効期限はトークンの `exp` で表現されている。

{/* { "id": "spec-rt-spent", "dependencies": ["spec-refresh-token"] } */}
### 7.2 使用済みトークン (再利用検知用)

キー
: `rt_spent:{sub}:{sid}`

データ型
: Sorted Set

スコア
: 各リフレッシュトークンの `exp` より 1 分長い値 (NumericDate)

メンバー
: 使用済みリフレッシュトークンの SHA-256 ハッシュ (base64)

{/* { "id": "spec-rt-spent-add", "dependencies": ["spec-rt-spent", "spec-refresh-swap"] } */}
#### 使用済みトークンの記録

*リフレッシュ* (`POST /refresh`) 時、古いリフレッシュトークンのハッシュをスコア付きで追加する。

~~~redis
ZADD rt_spent:{sub}:{sid} <old_rt_exp + 1m> <old_rt_hash>
~~~

Sorted Set の TTL (`EXPIREAT`) は現行トークンの `exp` よりも 1 分長く設定し、トークンを差し替えるたびに更新する。現行トークンと同じく、TTL はガベージコレクションのための値である。この TTL は、Sorted Set 内の最大スコア、すなわち直近に追加したメンバーのスコアと常に同期させる。
{/* TODO: 2文目の主張が不明 */}
`EXPIREAT` は独自のマージンを持つのではなく、このスコアのマージンにそのまま追従する。

{/* { "id": "spec-reuse-detection", "dependencies": ["spec-rt-spent", "spec-rt-current"] } */}
#### 再利用検知
{/* MARK: Reviewed Above */}

*リフレッシュ* (`POST /refresh`) において、提示されたリフレッシュトークンが `rt:{sub}:{sid}` と一致しない場合、次の手順で、再利用検知を行う:

1.  スコア (元のリフレッシュトークンの `exp` + 1m) が現在時刻以前のエントリを刈り取る。

    ~~~redis
    ZREMRANGEBYSCORE rt_spent:{sub}:{sid} 0 <現在時刻>
    ~~~

2.  提示トークンのハッシュがこの Sorted Set に含まれるかどうかを調べる。

    ~~~redis
    ZSCORE rt_spent:{sub}:{sid} <presented_rt_hash>
    ~~~

3.  `ZSCORE` が値を返した場合、その RT は**有効期限内かつ使用済み**であり、再利用が検知されたことを意味する。この場合は、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` を即座に削除し、セッションを強制終了する。

    ~~~redis
    MULTI
    DEL rt:{sub}:{sid}
    DEL rt_spent:{sub}:{sid}
    ~~~

4.  `ZSCORE` が NULL を返した場合、その RT は「未知の RT」または「既に期限切れで刈り取られた RT」である。セッションは終了させず、当該リクエストだけを `403 Forbidden` で拒否する。

この判定順序により、**有効期限内の使用済み RT のみ**が再利用として扱われる。

{/* { "id": "spec-sessions-index-ttl", "dependencies": ["spec-sessions-index", "spec-refresh-token"] } */}
### 7.3 セッションの索引

*アサーション結果受理* (`POST /assertion/result`) 時は、セッションの索引としてセッション ID と Credential ID のペアを保存し、フィールドの TTL を設定する。

~~~redis
HSET sessions:{sub} <sid> <credential_id>
HEXPIREAT sessions:{sub} <rt_exp + 1m> FIELDS 1 <sid>
~~~

*リフレッシュ* (`POST /refresh`) 時は、フィールドの TTL を延長する。

~~~redis
HEXPIREAT sessions:{sub} <new_rt_exp + 1m> FIELDS 1 <sid>
~~~

フィールドの TTL (`HEXPIREAT`) はセッションの有効期限、すなわち現行トークンの `exp` よりも 1 分長く設定し、リフレッシュのたびに更新する。現行トークン、使用済みトークンと同じく、TTL はガベージコレクションのための値であり、セッションの有効期限ではない。セッションの有効期限は現行トークンの `exp` で表現されている。

### A.2 原則

{/* { "id": "prin-encoding-by-use" } */}
#### 表示形式は用途で選ぶ

バイトデータの表示形式はそのデータの用途に応じて選ぶ。人が書き留めることがあるデータには base32 を、JWS や URL に載ることがあるデータには base64url を、それ以外のデータには base64 を用いる。個々のデータがどの形式で表示されるかは、そのデータの仕様に記述する。

### B.1 インフラ要件・データストアの根拠

{/* { "id": "why-same-site", "dependencies": ["spec-same-site"] } */}
#### 同一サイトに配置する理由

同一サイトでなければ、リフレッシュトークン (`SameSite=Strict` Cookie) が付加されず、*リフレッシュ* (`POST /refresh`) や*失効* (`POST /revoke`) が機能しなくなる。

{/* { "id": "why-code-hash-sha256", "dependencies": ["spec-recovery-codes-table", "spec-recovery-code-format"] */}
#### `code_hash` に SHA-256 を使用する理由

リカバリーコードは 128 ビット以上のエントロピーを持つため、仮に DB がダンプされたとしても、総当たり攻撃には平均 2¹²⁷ 回の試行を要する。これは現在最速の ASIC (Antminer S23 Hyd 3U; 1160 TH/S) を 100 万台並列しても、平均約 46 億 5000 万年かかる計算となる。

{/* { "id": "why-code-hash-unique", "dependencies": ["spec-recovery-codes-table", "spec-subject-id-not-memorized"] } */}
#### `code_hash` が一意性制約を持つ理由

ユーザーは主体の ID を記憶していないため、リカバリーコードを消費する際に、主体の ID を入力として受け取れない。そのため、`code_hash` のみを検索キーとしてレコードを特定する必要があり、`code_hash` は一意性制約を持つ。

{/* { "id": "why-session-id-csprng", "dependencies": ["spec-session-id"] } */}
#### セッション ID を CSPRNG で生成する理由

セッション ID はリフレッシュトークンの一部として発行され、署名されているため、たとえ攻撃者がセッション ID の推測に成功したとしても、リフレッシュトークンの署名を偽装したり、`rt:{sub}:{sid}` の値を盗取し、推測したセッション ID を含む有効なリフレッシュトークンを導出したりすることは事実上不可能である。

ただし、Active スロット ([5. 鍵ローテーション](#5-鍵ローテーション)) の秘密鍵が漏洩している場合、攻撃者は、対象セッションの `sid` を計算し、その `sid` を含むリフレッシュトークンを署名することで、既存のセッションを奪取できる。よって、セッション ID の暗号学的安全性は、既存セッション奪取に対する防禦層のひとつとして機能する。

{/* { "id": "why-ratelimit-nx", "dependencies": ["spec-ratelimit-all-endpoints"] } */}
#### `EXPIRE` に `NX` を指定する理由

時間窓を固定長にするため。

{/* { "id": "why-ratelimit-params-configurable", "dependencies": ["spec-ratelimit-all-endpoints"] } */}
#### 閾値と時間窓を規定しない理由

閾値と時間窓の長さは、攻撃の実態に応じて運用中に調整されうる値であるため。

{/* { "id": "why-sessions-index", "dependencies": ["spec-sessions-index", "spec-refresh-swap", "spec-sessions-revoke"] } */}
#### セッションの索引を主体ごとの Hash にする理由

リフレッシュで分かっているのは、`sub` と `sid` だけである。破棄で分かっているのは、`sub` と、破棄の対象のパスキーの `credential_id` だけである。そのため、`sid` から更新でき、`credential_id` から引ける、主体ごとの Hash とした。`credential_id` をキーに含める索引では、リフレッシュのとき、更新すべきキーを組み立てられない。また、`rt:{sub}:{sid}` の値は現行のリフレッシュトークンのハッシュであり、そこにパスキーの情報を足すと、値の意味が変わる。

{/* { "id": "why-sessions-index-gc", "dependencies": ["spec-sessions-index", "spec-sessions", "spec-sessions-revoke", "spec-sessions-revoke-all"] } */}
#### 索引のフィールドを削除せず TTL に任せる理由

終了したセッションのフィールドが残っていても、索引を使う処理は、`rt:{sub}:{sid}` の存在でセッションが生きているかを判定するので、一覧に現れず、破棄でも何も起きない。したがって、残っていても危険はなく、`POST /revoke`、再利用検知、破棄のそれぞれに、削除の処理を足す必要がない。
