# Sueka/Social 認証・認可の実装設計（design）

-   文書種別: 実装設計
-   状態: 分離作業中のドラフト
-   関連文書: `spec.md`、`rationale.md`

本書は `spec.md`
の規範的要件を実現するための内部構造と実装方法を記載する。実装方式を変更しても
`spec.md`
の外部契約・セキュリティ保証を維持する限り、必ずしも本書の構造を維持する必要はない。

## 1. コンポーネントと配置

### 1.1 コンポーネント

  ------------------------------------------------------------------------------------------------------------------------
  名称                                実装責務
  ----------------------------------- ------------------------------------------------------------------------------------
  認証サービス                        WebAuthn
                                      の登録・認証、主体・認証器・リカバリーコードの管理、トークン発行、署名鍵管理、JWKS
                                      公開

  クライアントアプリ                  登録・認証 UI、認証器とのやり取り、認証トークンの提示

  機能サービス                        JWKS 取得・キャッシュ、認証トークンの検証、セッション種別に応じた制限

  認証器                              クレデンシャル鍵ペア生成とアテステーション／アサーションの返却。本システム外
  ------------------------------------------------------------------------------------------------------------------------

認証サービスとクライアントアプリは WebAuthn Relying Party を構成する。

### 1.2 配置

クライアントアプリと認証サービスは同一サイト（eTLD+1
が同一）に配置する。認証サービスの前段にリバースプロキシを配置するかどうかはデプロイ環境の構成とする。プロキシが存在する場合のクライアント
IP アドレスの取得元（ヘッダー名を含む）は設定値とする。

## 2. RDB スキーマ

### 2.1 `subjects`

  カラム     型          説明
  ---------- ----------- ----------
  `id`       `uuid`      主体 ID
  `frozen`   `boolean`   凍結状態

主体は UUID の ID
のみを持ち、ユーザー名やメールアドレスなどの属性を保持しない。

### 2.2 `passkeys`

  カラム            型                           説明
  ----------------- ---------------------------- ------------------------------------------
  `subject_id`      `subjects.id` への外部キー   主体 ID
  `credential_id`   `bytea`                      認証器の Credential ID
  `passkey_text`    `text`                       公開鍵やカウンターなどを含むパスキー情報
  `last_used_at`    `timestamptz`                最終使用日時
  `revoked_at`      `timestamptz`                失効日時。NULL は有効

### 2.3 `recovery_codes`

  ----------------------------------------------------------------------------
  カラム                  型                      説明
  ----------------------- ----------------------- ----------------------------
  `subject_id`            `subjects.id`           主体 ID
                          への外部キー

  `code_hash`             `text`                  リカバリーコードの SHA-256
                                                  ハッシュ（base64）。UNIQUE

  `used_at`               `timestamptz`           使用日時。NULL は未使用

  `revoked_at`            `timestamptz`           失効日時。NULL は有効
  ----------------------------------------------------------------------------

リカバリーコードの消費は単一の SQL UPDATE で実装する。

``` sql
UPDATE recovery_codes
SET used_at = :now
WHERE code_hash = :code_hash
  AND used_at IS NULL
  AND revoked_at IS NULL;
```

更新行数が 1 行なら消費成功、0
行なら存在しないか、使用済み、または失効済みとして扱う。

リカバリーコード再発行時は、新規コードの発行に先立って未使用コードを失効させる。

``` sql
UPDATE recovery_codes
SET revoked_at = :now
WHERE subject_id = :sub
  AND used_at IS NULL
  AND revoked_at IS NULL;
```

### 2.4 登録時の永続化

登録時は主体、パスキー、リカバリーコードのハッシュを保存する。元文書では、これらの保存を原子的に行うことが推奨されていた。実装ではトランザクションを用いる案があるが、必須性と失敗時の回復方針は未決定事項として残す。

## 3. インメモリ KVS

### 3.1 セッション状態

  -------------------------------------------------------------------------------
  キー                     型                      値
  ------------------------ ----------------------- ------------------------------
  `rt:{sub}:{sid}`         String                  現行 RT の SHA-256
                                                   ハッシュ（base64）

  `rt_spent:{sub}:{sid}`   Sorted Set              使用済み RT の SHA-256
                                                   ハッシュ（base64）。スコアは
                                                   RT の `exp` + 1 分
  -------------------------------------------------------------------------------

`{sub}` は主体 ID の大文字 hex-and-dash 表現、`{sid}` は base64url
表現とする。

### 3.2 セッション ID

セッション ID は `/assertion/result` または `/recovery` 成功時に RT
の一部として生成する。同じ主体の別セッションには別の `sid`
を割り当てる。同一セッションではリフレッシュ時に `sid`
を引き継ぐ。生成には 128 ビット以上のエントロピーを持つ CSPRNG
を用い、base64url で表現する。

### 3.3 リカバリーのレート制限カウンター

  キー                        型       値
  --------------------------- -------- ------------------------
  `ratelimit:recovery:{ip}`   String   固定時間窓内の試行回数

実装例:

``` redis
MULTI
INCR ratelimit:recovery:{ip}
EXPIRE ratelimit:recovery:{ip} <時間窓の長さ> NX
EXEC
```

`INCR` の結果がしきい値を超えた場合は `429 Too Many Requests`
を返す。`EXPIRE NX` により TTL
は時間窓の先頭でのみ設定される。しきい値と時間窓は設定可能な運用パラメーターとする。

## 4. トークン実装

### 4.1 トークンのフィールド

AT/RCAT は `typ`、`alg`、`kid` ヘッダーと `sub`、`iat`、`exp`
クレームを持つ。RT はそれらに加えて `sid` を持ち、`typ` は `rt+jwt`
とする。`kid` は JWK Thumbprint（base64url）とする。

### 4.2 認証トークンの保存

元文書には、クライアントアプリが AT/RCAT を Session Storage、Local
Storage、またはそれに準ずる場所に保存する案がある。メモリだけに保存するとブラウザー再読み込みでトークンが失われ、リフレッシュや失効が行えなくなるという理由が挙げられている。ただし、元文書に
TODO が残っているため、保存方式は確定設計ではない。

### 4.3 リフレッシュトークンの配送

RT は次の Cookie で配送する。

``` http
Set-Cookie: refresh_token=<リフレッシュトークン>; HttpOnly; Secure; SameSite=Strict; Max-Age=86400; Path=/
```

## 5. 署名鍵管理

### 5.1 鍵スロット

認証サービスはメモリ上に以下の鍵スロットを保持する。

  --------------------------------------------------------------------------------------------------
  スロット                            内容
  ----------------------------------- --------------------------------------------------------------
  Active                              現在の署名・検証に使用する鍵の秘密鍵と公開鍵。常に 1 組

  Retired                             過去に署名に使用した鍵の公開鍵と削除可能時刻のリスト。複数可
  --------------------------------------------------------------------------------------------------

各鍵は、鍵種別（`kty`/`crv`）だけでなく、生成時に明示的に選択・宣言された署名アルゴリズムを保持する。移行期間中は異なる鍵種別の鍵が共存しうる。

### 5.2 平時ローテーション

現在の Active 鍵を A、新しい鍵を X とする。

1.  鍵 A の公開鍵と削除可能時刻を Retired に追加する。
2.  削除可能時刻は、現在時刻 + RT の有効期限 + AT/RCAT の有効期限 + 1
    分とする。
3.  Active 鍵を X に置き換える。
4.  JWKS は Active と、削除可能時刻を過ぎていないすべての Retired
    公開鍵の和集合を返す。

手順 1 の直後、一時的に鍵 A が Active と Retired
の両方に存在する場合がある。JWKS
の応答に同一公開鍵が重複する可能性がある。

### 5.3 緊急ローテーション

鍵漏洩が疑われる場合:

1.  Retired スロットの鍵をすべて削除する。
2.  Active 鍵を新しい鍵 X に置き換える。

緊急ローテーション後、旧鍵で署名された RT
は検証できない。旧鍵で署名された AT/RCAT は有効期限が切れるまで（最大 5
分）利用可能性が残る。

## 6. リフレッシュ実装

### 6.1 受け入れ処理

`POST /refresh` は以下の順序で処理する。

1.  RT の署名を検証する。
2.  RT の `typ` が `rt+jwt` であることと、`exp`
    が期限内であることを確認する。
3.  `rt:{sub}:{sid}` を読み、提示 RT
    のハッシュが現行値と一致することを確認する。
4.  一致しない場合、使用済み RT
    の記録から期限切れエントリを刈り取ったうえで、提示 RT
    のハッシュが記録に含まれるか確認する。
5.  有効期限内の使用済み RT であれば `rt:{sub}:{sid}` と
    `rt_spent:{sub}:{sid}` を削除し、セッションを終了する。未知の RT
    または既に期限切れの RT は当該リクエストのみ拒否する。
6.  AT/RCAT の署名、`typ`、`sub` の一致を検証する。
7.  AT/RCAT の `iat` が RT の `iat` 以前であることを確認する。
8.  AT の場合は主体が凍結されていないことを確認する。RCAT
    の場合は凍結状態による拒否を行わない。
9.  新しい同種の AT/RCAT と RT を発行し、KVS の状態を更新する。

### 6.2 使用済み RT の記録

RT のリフレッシュ成功時に、古い RT のハッシュを次のように Sorted Set
に追加する。

``` redis
ZADD rt_spent:{sub}:{sid} <old_rt_exp + 1m> <old_rt_hash>
```

現行 RT の保存期限は、新 RT の `exp` より 1 分長くする。使用済み RT の
Sorted Set の TTL は、現行 RT の `exp` より 1 分長く設定し、RT
を差し替えるたびに更新する。

### 6.3 再利用検知

1.  `exp + 1m` が現在時刻以前の使用済み RT エントリを削除する。

``` redis
ZREMRANGEBYSCORE rt_spent:{sub}:{sid} 0 <現在時刻>
```

2.  提示 RT のハッシュを検索する。

``` redis
ZSCORE rt_spent:{sub}:{sid} <presented_rt_hash>
```

3.  値が返った場合、提示 RT は期限内の使用済み RT
    である。セッション状態を原子的に削除する。

``` redis
MULTI
DEL rt:{sub}:{sid}
DEL rt_spent:{sub}:{sid}
EXEC
```

4.  NULL の場合は、未知または期限切れの RT
    として当該リクエストのみ拒否する。

### 6.4 並列リクエストと原子更新

同一セッションに対する並列リフレッシュの競合を検出するため、`rt:{sub}:{sid}`
を楽観ロックする。

``` redis
WATCH rt:{sub}:{sid}
GET rt:{sub}:{sid}
```

現行 RT の差し替えと使用済み RT の記録は、同一の原子操作で実行する。

``` redis
MULTI
SET rt:{sub}:{sid} <new_hash> EXAT <new_exp + 1m>
ZADD rt_spent:{sub}:{sid} <old_exp + 1m> <old_hash>
EXPIREAT rt_spent:{sub}:{sid} <old_exp + 1m>
```

`SET` と `ZADD` を原子的に行うことで、有効期限内の RT
ハッシュが現行集合と使用済み集合を合わせて適切に管理される。競合が検出されたリクエストは
`409 Conflict` とする。

## 7. 失効実装

`POST /revoke` では、RT の署名を検証し、セッションストアの現行 RT
ハッシュと照合する。AT/RCAT の署名と種別も検証し、両トークンの `sub`
が一致する場合に限り、RT に対応するセッション状態を削除する。

KVS エントリが既に削除されている場合、または提示 RT
のハッシュが現行値と一致しない場合は no-op
として処理する。監査ログには実際の削除と no-op を区別して記録する。

## 8. WebAuthn とエンドポイントの内部処理

### 8.1 `POST /attestation/options`

1.  主体 ID を生成する。
2.  CCO を構築する。
3.  登録状態と主体 ID をセッションストアに保存する。
4.  セッション ID を Cookie に付加し、CCO を応答する。

空の `username` または `displayName` の扱いは `spec.md` を参照する。

### 8.2 `POST /attestation/result`

1.  受信したアテステーション署名を検証する。
2.  主体とパスキーを RDB に保存する。
3.  リカバリーコードを 10 個生成する。
4.  コードのハッシュを RDB に保存し、平文コードを応答する。

### 8.3 `POST /assertion/options`

1.  CRO を構築する。
2.  認証状態をセッションストアに保存する。
3.  セッション ID を Cookie に付加し、CRO を応答する。

### 8.4 `POST /assertion/result`

1.  認証アサーションを検証する。
2.  対象パスキーが未失効であることを確認する。
3.  主体が凍結されていないことを確認する。
4.  `sid` を生成する。
5.  AT と RT を発行する。
6.  RT のハッシュを `rt:{sub}:{sid}` に保存する。
7.  AT を応答し、RT を Cookie で返す。

### 8.5 `GET /.well-known/jwks.json`

Active 鍵と、削除可能時刻を過ぎていない Retired 鍵の公開鍵を JWK Set
として返す。各 JWK は `alg` と `kid` を含む。

### 8.6 `POST /recovery`

1.  IP 単位のレート制限を確認する。
2.  `code_hash` でリカバリーコードを検索する。
3.  未使用かつ有効なコードを原子的に消費する。
4.  `sid` を生成する。
5.  RCAT と RT を発行する。
6.  RT のハッシュを `rt:{sub}:{sid}` に保存し、RCAT と RT を返す。

### 8.7 `POST /recoveryCodes/reissue`

1.  AT の署名、有効期限、`typ` を検証する。
2.  未使用のリカバリーコードを失効させる。
3.  新しいコードを 10 個生成し、ハッシュを RDB に保存する。
4.  平文コードを応答する。

### 8.8 `GET /passkeys`

AT の署名、有効期限、`typ`
を検証し、主体に紐づく有効なパスキーを検索して一覧を返す。失効済みパスキーは除外する。

### 8.9 `POST /passkeys/revoke`

AT の署名、有効期限、`typ` を検証し、`subject_id` と `credential_id`
に一致する有効なパスキーを検索する。他の有効なパスキーが存在する場合に限り、対象の
`revoked_at` を記録する。昇格認証の要否は未決定であり、`spec.md` と
`rationale.md` の未決定事項を参照する。

## 9. クライアント実装上の注意

クライアントアプリは AT の `exp`
を基準に能動的なリフレッシュを試みない。認証トークンの期限切れを示す応答を受け取った場合に
`POST /refresh` を呼び出し、成功時に元の呼び出しを再試行してよい。

## 10. 未決定の実装事項

-   AT/RCAT のブラウザー側保存方式。
-   登録時の複数レコード保存を原子的にするか、障害時にどう回復するか。
-   高リスク操作に対する昇格認証の実現方式。
-   レート制限で使用するクライアント IP の取得元と信頼境界。
