### 1.4 インフラ要件

クライアントアプリと認証サービスは同一サイト (eTLD+1 が同一のドメイン) に配置する。同一サイトでなければ、リフレッシュトークン (`SameSite=Strict` Cookie) が付加されず、*リフレッシュ* (`POST /refresh`) や*失効* (`POST /revoke`) が機能しなくなる。

認証サービスの手前にリバースプロキシ等を配置するかどうかは、デプロイ環境ごとの構成として扱う ([3.2 インメモリ KVS](#32-インメモリ-kvs) のレート制限カウンターを参照)。

## 2. 認証方式

通常の認証方式はパスキー (Discoverable Credentials) のみとする。ID・パスワード認証やその他の認証方式は提供されない。

認証器をすべて失ったときのためのデータ保全手段として、リカバリーコードによる認証を提供する。リカバリーコードによる認証は通常のセッションを開始せず、代わりにリカバリーセッションを開始する。リカバリーセッションで行えることはユーザーデータの取得と削除申請のみである。

## 3. データストア

### 3.1 RDB

認証主体と認証器に関する情報を保持する。

#### 主体テーブル (subjects)

| カラム   | 型      | 説明                 |
| -------- | ------- | -------------------- |
| `id`     | uuid    | 主体の ID            |
| `frozen` | boolean | 凍結されているか否か |

主体は **ID のみの存在**であり、ユーザー名やメールアドレスなどの追加の属性を持たない。主体の ID は UUID であるため、<u>ユーザーが主体の ID を記憶している</u>と想定することはできない。

{/* TODO: 「に対する」でよいか */}
凍結された主体に対する*アサーション結果受理* (`POST /assertion/result`) と、凍結された主体に対するログインセッションの*リフレッシュ* (`POST /refresh`) は拒否される。リカバリーはユーザーデータへのアクセス権を保障するための機能であるため、リカバリーセッションのリフレッシュは拒否されない。認証トークンはステートレスであるため、発行済みのものは最大 5 分間行使できる。

#### パスキーテーブル (passkeys)

| カラム          | 型          | 説明                                      |
| --------------- | ----------- | ----------------------------------------- |
| `subject_id`    |             | 主体の ID (`subjects.id` の外部キー)      |
| `credential_id` | bytea       | 認証器の Credential ID                    |
| `passkey_text`  | text        | パスキー情報 (公開鍵やカウンターなどを含む) |
| `last_used_at`  | timestamptz | 最終使用日時                              |
| `revoked_at`    | timestamptz | 失効日時 (NULL: 有効)                     |

#### リカバリーコードテーブル (recovery_codes)

| カラム       | 型          | 説明                                                 |
| ------------ | ----------- | ---------------------------------------------------- |
| `subject_id` |             | 主体の ID (`subjects.id` の外部キー)                 |
| `code_hash`  | text        | リカバリーコードの SHA-256 ハッシュ (base64, UNIQUE) |
| `used_at`    | timestamptz | 使用日時 (NULL: 未使用)                              |
| `revoked_at` | timestamptz | 失効日時 (NULL: 有効)                                |

リカバリーコードは登録時に 10 個発行される。各リカバリーコードは一度しか使用できない。

リカバリーコードは 128 ビット以上のエントロピーを持つ CSPRNG で生成される。書き留めることがあるため、表示形式は **base32** を用いる。

`code_hash` は一意性制約を持つ。ユーザーは主体の ID を記憶していないため、リカバリーコードを消費する際は、`code_hash` のみを検索キーとしてレコードを特定する必要がある。

`code_hash` には SHA-256 を使用する。リカバリーコードは 128 ビット以上のエントロピーを持つため、仮に DB がダンプされたとしても、総当たり攻撃には平均 2¹²⁷ 回の試行を要する。これは現在最速の ASIC (Antminer S23 Hyd 3U; 1160 TH/S) を 100 万台並列しても、平均約 46 億 5000 万年かかる計算となる。

### 3.2 インメモリ KVS

認証サービスの一時的な状態を管理する。次の 2 つの用途で使用する。

#### セッション管理 (`rt` / `rt_spent`)

| キー                   | データ型   | 説明                                                   |
| ---------------------- | ---------- | ------------------------------------------------------ |
| `rt:{sub}:{sid}`       | String     | 現在有効なリフレッシュトークンの SHA-256 ハッシュ       |
| `rt_spent:{sub}:{sid}` | Sorted Set | 使用済みリフレッシュトークンの SHA-256 ハッシュの集合   |

`{sub}` は主体の ID (大文字 hex-and-dash)、`{sid}` はセッション ID (base64url) である。

##### セッション ID

セッション ID は、*アサーション結果受理* (`POST /assertion/result`) または*リカバリーコードによる認証* (`POST /recovery`) 成功時、リフレッシュトークンの一部として発行される。同一の主体が確立したセッションであっても、別々に確立されたセッションは異なるセッション ID を持つ。セッション ID はセッションを通じて一定であり、リフレッシュ時に引き継がれる。

セッション ID は 128 ビット以上のエントロピーを持つ CSPRNG で生成される。JWS に載ることがあるため、表示形式は base64url を用いる。

セッション ID はリフレッシュトークンの一部として発行され、署名されているため、たとえ攻撃者がセッション ID の推測に成功したとしても、リフレッシュトークンの署名を偽装したり、`rt:{sub}:{sid}` の値を盗取し、推測したセッション ID を含む有効なリフレッシュトークンを導出したりすることは事実上不可能である。

#### レート制限カウンター (`ratelimit:recovery`)

| キー                      | データ型 | 説明                                                                          |
| ------------------------- | -------- | ----------------------------------------------------------------------------- |
| `ratelimit:recovery:{ip}` | String   | *リカバリーコードによる認証* (`POST /recovery`) における、時間窓内の試行回数 |

`{ip}` はクライアントの IP アドレスの正規化された文字列表現である。認証サービスの手前にリバースプロキシ等が存在する構成では、TCP 接続元の IP アドレスは実クライアントのものではなくなるため、`{ip}` の取得元(ヘッダー名を含む)は設定可能なパラメーターとする。

*リカバリーコードによる認証* (`POST /recovery`) の受信時、次の手順で IP アドレス単位の固定時間窓カウンターを更新する。

~~~redis
MULTI
INCR ratelimit:recovery:{ip}
EXPIRE ratelimit:recovery:{ip} <時間窓の長さ> NX
EXEC
~~~

`INCR` の結果がしきい値を超えている場合、`429 Too Many Requests` を返す。`EXPIRE` に `NX` を指定することで、TTL は時間窓の先頭でのみ設定され、以降のインクリメントでは延長されない。これにより、時間窓は固定長となる。

しきい値および時間窓の長さは、攻撃の実態に応じて運用中に調整されうる値であるため、本書では具体的な数値を規定せず、設定可能なパラメーターとする。

## 4. トークン

認証結果は次の JWS (JSON Web Signature) トークンで表現される:

| トークン                      | 有効期限 |
| ----------------------------- | -------- |
| 通常の認証トークン (AT)       | 5 分     |
| リカバリー認証トークン (RCAT) | 5 分     |
| リフレッシュトークン (RT)     | 1 日     |

### 4.1 認証トークン

認証トークンは**認証事実**を表現する。

*アサーション結果受理* (`POST /assertion/result`)、*リフレッシュ* (`POST /refresh`) または*リカバリーコードによる認証* (`POST /recovery`) の結果として発行される。有効期限は 5 分間。
{/* 認証トークンの有効期限は、認証要素 (認証器、リフレッシュトークンまたはリカバリーコード) の認証力の減衰に対する許容時間窓として機能する。 */}

#### ヘッダー

| パラメーター | 型     | 説明                                |
| ------------ | ------ | ----------------------------------- |
| `typ`        | string | 認証トークンの種類により異なる。    |
| `alg`        | string | 署名に利用した署名アルゴリズム      |
| `kid`        | string | 署名鍵の JWK Thumbprint (base64url) |

#### ペイロード

| クレーム | 型     | 説明                                |
| -------- | ------ | ----------------------------------- |
| `sub`    | string | 認証主体の ID (大文字 hex-and-dash) |
| `iat`    | number | 発行時刻 (NumericDate)              |
| `exp`    | number | 有効期限 (NumericDate)              |

#### 4.1.1 通常の認証トークン

ログインセッションで使用する認証トークン。単に AT (Authentication Token) とも表記する。

##### ヘッダー

| パラメーター | 型     | 説明       |
| ------------ | ------ | ---------- |
| `typ`        | string | `"at+jwt"` |

#### 4.1.2 リカバリー認証トークン

リカバリーセッションで使用する認証トークン。RCAT (Recovery-Context Authentication Token) とも表記する。通常の認証トークンとほとんど同じヘッダーとペイロードを持つが、`typ` の値が異なる。

##### ヘッダー

| パラメーター | 型     | 説明         |
| ------------ | ------ | ------------ |
| `typ`        | string | `"rcat+jwt"` |

#### 保存方法

クライアントアプリは、認証トークンを Session Storage もしくは Local Storage またはそれに準ずる場所に保存する。メモリに保存すると、ブラウザーの再読み込みによって認証トークンが失われ、*リフレッシュ*および*失効*が行えなくなる。

#### 認証条件

認証トークンとして提示されたトークンが次の条件をすべて満たすとき、かつそのときに限り、そのトークンの `sub` で表される主体が*認証されている*と見做す:

- そのトークンが*正規の公開鍵*によって検証される
- そのトークンが*認証トークン*である (`typ` が `"at+jwt"` / `"rcat+jwt"` である)
- そのトークンが期限切れでない (`exp` が現在時刻よりも後である)
- そのトークンの `alg` が `"none"` でない
- そのトークンの `alg` が、そのトークンのヘッダーの `kid` に対応する鍵に紐づけられた署名アルゴリズムの名称と一致する

正規の公開鍵は次のものをいう:

- 認証サービスでは、*Active スロット*の鍵と、現在時刻が削除可能時刻を越えていない全ての *Retired スロット*の鍵。各鍵には、鍵の種類 (`kty`/`crv`) によらず、生成時に明示的に選択・宣言された署名アルゴリズムが紐づく ([5.1 鍵スロットの構成](#51-鍵スロットの構成) を参照)。
- 機能サービスでは、*JWKS エンドポイント*から取得した JWK またはそのキャッシュ。署名アルゴリズムは、その JWK 自身の `alg` フィールドの値とする。

トークンが正規の公開鍵によって*検証される*とは、`kid` に対応する鍵に紐づけられた署名アルゴリズムを用いて、そのトークンの署名が有効であることが確認できることをいう。このとき、検証に使用する署名アルゴリズムを、トークンのヘッダーの `alg` から選択してはならない。これに反すると、鍵の種類によっては Alg Confusion が成立しうる。

機能サービスは、認証トークンの `typ` に応じて、セッション種別を区別する。

- `typ` が `"at+jwt"` の場合は通常セッションとして扱う。
- `typ` が `"rcat+jwt"` の場合はリカバリーセッションと判断し、ユーザーデータの取得と削除申請のみを許可する。

機能サービスは、署名検証の実装にあたっては、次の要件を満たさなければならない:

- 検証に使用する鍵は、ヘッダーの `kid` と JWKS の各鍵エントリの `kid` を照合して特定する
- 未知の `kid` を含むトークンを受信した場合、キャッシュの状態によらず、JWKS エンドポイントを即時に再取得する

> **注記 (クロックスキュー):** 本システムのインフラでは認証サービスと機能サービスのシステム時刻は一致しているため、クロックスキューは実用上の問題にならない。分散環境では許容スキュー (例: ±30 秒) を設けることが慣行だが、有効期限切れのトークンを意図的に受け入れる実装はモラルハザードのリスクを伴うため、本仕様では採用しない。

## 5. 鍵ローテーション

### 5.1 鍵スロットの構成

認証サービスはメモリ上に次の鍵を保持する:

| スロット名  | 説明                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| **Active**  | 現在トークンの署名・検証に使用している鍵。秘密鍵と公開鍵を保持する。同時に 1 組存在する。                |
| **Retired** | 過去トークンの署名に使用していた鍵。公開鍵と削除可能時刻のペアのリストを保持する。同時に複数存在しうる。 |

各鍵は、鍵の種類 (`kty`/`crv`) に加えて、その鍵とともに生成時に明示的に選択・宣言された署名アルゴリズムを保持する。署名アルゴリズムは鍵の種類から自動的に導出しない。鍵の種類と署名アルゴリズムの組は、JWKS では JWK の `kty`/`crv` と `alg` として表れる。

移行期間中は、Active・Retired の各スロットに、異なる鍵の種類 (たとえば EC と OKP) の鍵が混在しうる。


### 5.2 手順

現在各スロットにある鍵を次のように呼ぶ:

| スロット      | 現在の鍵         |
| ------------- | ---------------- |
| Active        | 鍵 A             |
| Retired       | 鍵 B₁, 鍵 B₂, … |

新たに投入する鍵を **鍵 X** とする。

#### 5.2.1 平時ローテーション

1.  鍵 A の公開鍵と削除可能時刻のペアを Retired スロットに追加する。削除可能時刻は、*現在時刻 + リフレッシュトークンの有効期限 + 認証トークンの有効期限 + 1 分* とする。
2.  Active スロットの鍵を鍵 X で置き換える。

削除可能時刻はガベージコレクションのための値であり、鍵の失効時刻ではない。有効期限内のトークンはすべて鍵 A で検証可能である必要があるため、削除可能時刻を迎えるまでは鍵 A の公開鍵を JWKS のレスポンスに含め続けなければならない。

手順 1 の直後、一時的に鍵 A が Active スロットと Retired スロットの両方に存在するタイミングがあるが、JWKS エンドポイントは両スロットの公開鍵の和集合を返すため、同じ鍵が重複して含まれるだけで実害はない。

#### 5.2.2 緊急ローテーション

鍵の漏洩が疑われる場合に実行する。

1.  Retired スロットの鍵をすべて削除する。
2.  Active スロットの鍵を鍵 X で置き換える。

Active スロットと Retired スロットの鍵はいずれも、同一の認証サービスプロセスのメモリ上に保持されている ([5.1 鍵スロットの構成](#51-鍵スロットの構成)) ところ、メモリダンプやプロセス侵害など、鍵漏洩を引き起こす典型的な事象は、ある特定の 1 つの鍵ではなく、その時点でメモリ上に存在する鍵をまとめて暴露する。したがって、漏洩範囲が特定の 1 つの鍵に限定できるという前提を置くことはできないため、削除する鍵を限定したローテーション手順は規定しない。

緊急ローテーション完了後、過去に鍵 A, 鍵 B₁, 鍵 B₂, … で署名されたリフレッシュトークンは即時検証不可となる。旧鍵で署名された認証トークンは有効期限 (最大 5 分) 以内に自然失効する。

#### 認証トークンの役割

`POST /refresh` における認証トークンには、リフレッシュ対象の主体が認証済みの主体であることを確認する役割がある。

リフレッシュとは認証済みの主体の再認証である。リフレッシュトークンはリフレッシュの認可を表現するものであり、認証事実を表現するものではない。リフレッシュトークンは認証事実を表現しないため、リフレッシュトークンの `sub` は認証済みの主体ではなく、単にリフレッシュ対象の主体を表す。したがって、リフレッシュを行うには、リフレッシュ対象の主体が認証済みの主体であることを確認する必要がある。そこで、認証済みの主体を示すものとして、認証トークンの `sub` を用いる。

また、認可は認証済みの主体に対して与えられるものであるから、認証トークンはリフレッシュトークンと同時に、あるいはより早く発行されたものである必要がある。

#### 並列リクエスト対策

同一セッションに対する `POST /refresh` が並列に呼び出されても KVS エントリの更新が競合しないよう、`rt:{sub}:{sid}` を楽観ロックする。なお、厳密には `rt_spent:{sub}:{sid}` の更新も競合しうるが、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` は原子的に更新されるため、監視するキーはいずれか 1 つで十分である。

~~~redis
WATCH rt:{sub}:{sid}
GET rt:{sub}:{sid}
~~~

#### 現行トークンの差し替えの原子性

現行トークンの差し替えは原子的に行う必要がある。

~~~redis
MULTI
SET rt:{sub}:{sid} <new_hash> EXAT <new_exp + 1m>
ZADD rt_spent:{sub}:{sid} <old_exp + 1m> <old_hash>
EXPIREAT rt_spent:{sub}:{sid} <old_exp + 1m>
~~~
{/* MARK: Reviewed Above */}

- `SET` と `ZADD` は原子的に行う。有効期限内のリフレッシュトークンのハッシュは、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` を合わせて、常にちょうど 1 つ保持される。
- `SET` と `EXPIREAT` は原子的に行う。`rt_spent:{sub}:{sid}` は、現行トークンが有効である間、使用済みトークンとして検出すべきリフレッシュトークンのハッシュを保持する。
- `ZADD` と `EXPIREAT` は当然原子的に行う。

#### クライアントアプリ実装上の注意

クライアントアプリは、認証トークンの `exp` を基準に能動的なリフレッシュを試みてはならない。

クライアントアプリは、認証トークンの期限切れを示す応答を受け取った場合、`POST /refresh` の実行、およびそれが成功した場合の元の呼び出しの再試行を行うことができる。

#### レスポンス

成功時は `200 OK` を返す。`Content-Type` は `application/json` とする。提示された認証トークンと同種のトークンが返る。

~~~json
{
  "auth_token": "<認証トークン>"
}
~~~

リフレッシュトークンは `Set-Cookie` ヘッダーで返す。

#### リクエスト

| 場所            | 名前            | 内容                      |
| --------------- | --------------- | ------------------------- |
| Cookie          | `refresh_token` | リフレッシュトークン      |
| JSON コンテント | `auth_token`    | 認証トークン (期限切れ可) |

#### 処理フロー

~~~mermaid
---

    layout: elk
    look: handDrawn
    flowchart:
        curve: basis
---
flowchart TD
    N10([POST /revoke 受信])
    N10 --> N20{RT の署名検証}
    N20 --> |失敗| ERR1([403 Forbidden])
    N20 --> |成功| N30[/"rt:{sub}:{sid} を取得"/]

    N50 --> |失敗| ERR4([401 Unauthorized])
~~~

#### 冪等性

`rt:{sub}:{sid}` が既に削除されている場合、または提示されたリフレッシュトークンのハッシュが現在の値と一致しない場合、`403 Forbidden` ではなく `200 OK` を返す。これにより、同一のリフレッシュトークンを用いた複数回の `POST /revoke` 呼び出しは冪等となる。ただし、実際に `rt:{sub}:{sid}` を削除した場合と、削除対象が存在しなかった場合とは、監査ログ上は区別して記録する ([8.1 記録対象イベント](#81-記録対象イベント) を参照)。

#### レスポンス

成功時は `200 OK` を返す。

`POST /refresh` との対称性のため、`Content-Type` は `application/json`、ボディは `{}` とする。AT と RT の `sub` が一致する場合、リフレッシュトークンの Cookie は `Max-Age=0` によりクライアント側でも削除する。

~~~http
Set-Cookie: refresh_token=; HttpOnly; Secure; SameSite=Strict; Max-Age=0; Path=/
~~~

AT と RT の `sub` が不一致の場合、セッションには何もせずに `200 OK` を返す。この状態では `POST /refresh` は失敗し、クライアントは RT を用いた再認証ができない。認証トークンの有効期限 (最大 5 分) が切れた時点で認証は自然に終了する。

#### 認証トークンの役割

`POST /revoke` における認証トークンには、`POST /refresh` の場合と同様、失効対象の主体が認証済みの主体であることを確認する役割がある。

リフレッシュとは異なり、リフレッシュトークン以前に発行されたことは要求しない。

### 6.8 リカバリーコードによる認証エンドポイント

~~~
POST /recovery
~~~

リカバリーコードを受け取って、リカバリー認証トークンとリフレッシュトークンを発行し、リカバリーセッションを開始する。リカバリーセッションは凍結中の主体でも開始できる。リカバリーはユーザーデータへのアクセス権を保障するための機能であり、凍結によっても制限されない。

#### レート制限

ブルートフォース攻撃を防ぐため、IP アドレス単位のレート制限を適用する ([3.2 インメモリ KVS](#32-インメモリ-kvs) を参照)。レート制限も到達の前提の一部であるため、`recovery_code` を消費するよりも前に判定する。制限を超えた場合は `429 Too Many Requests` を返す。この判定は `recovery_code` を参照する前に行われるため、コードの存在有無について何の情報も持たない。

#### リクエスト

| 場所            | 名前            | 内容             |
| --------------- | --------------- | ---------------- |
| JSON コンテント | `recovery_code` | リカバリーコード |

#### 処理フロー

~~~mermaid
---
config:
    layout: elk
    look: handDrawn
    flowchart:
        curve: basis
---
flowchart TD
    N10([POST /recovery 受信])
    N10 --> N15{IP 単位のレート制限を超過していないか}
    N15 --> |超過| ERR3([429 Too Many Requests])
    N15 --> |範囲内| N20[(recovery_codes を code_hash で検索)]
    N20 --> |存在しない| ERR1([401 Unauthorized])
    N20 --> |存在する| N30[(未使用かつ有効なら used_at を記録)]
    N30 --> |更新 0 行| ERR2([401 Unauthorized])
    N30 --> |更新 1 行| N45[sid を生成]
    N45 --> N50[RCAT と RT を発行]
    N50 --> N55[/"発行した RT のハッシュを rt:{sub}:{sid} に保存"/]
    N55 --> N60{{RCAT を応答コンテントに付加}}
    N60 --> N70{{RT を Set-Cookie に付加}}
    N70 --> N80([200 OK])
~~~

リカバリーコードの消費 (`used_at` の確認と記録) は**単一の原子操作**として実行する。

~~~sql
UPDATE recovery_codes
SET used_at = :now
WHERE code_hash = :code_hash
AND used_at IS NULL
AND revoked_at IS NULL;
~~~

`used_at` の確認と記録が原子的でないと、並列リクエストによって、同じリカバリーコードが二重に使用される可能性がある。

#### レスポンス

成功時は `200 OK` を返す。`Content-Type` は `application/json` とする。

~~~json
{
  "auth_token": "<RCAT>"
}
~~~

リフレッシュトークンは `Set-Cookie` ヘッダーで返す。

## 7. セッション管理

セッションの失効とリフレッシュトークンの再利用検知を実現するために、現行トークンと使用済みトークンのハッシュをセッションストアに保持する。

### 7.1 現行トークン

キー
: `rt:{sub}:{sid}`

値
: 現在有効なリフレッシュトークンの SHA-256 ハッシュ (base64)

TTL はリフレッシュトークンの `exp` よりも 1 分長く設定する。セッションストア上の TTL はガベージコレクションのための値であり、トークンの有効期限ではない。トークンの有効期限はトークン自体の `exp` で表現されている。TTL が `exp` と同一の場合、`exp` 間際に試行された正当なリフレッシュが KVS エントリの消滅によって拒否されるおそれがある。

### 7.2 使用済みトークン (再利用検知用)

キー
: `rt_spent:{sub}:{sid}`

データ型
: Sorted Set

スコア
: 各リフレッシュトークンの `exp` より 1 分長い値 (NumericDate)

メンバー
: 使用済みリフレッシュトークンの SHA-256 ハッシュ (base64)

#### リフレッシュ成功時

リフレッシュ成功時、古いリフレッシュトークンのハッシュをスコア付きで追加する。

~~~redis
ZADD rt_spent:{sub}:{sid} <old_rt_exp + 1m> <old_rt_hash>
~~~

Sorted Set 自体の TTL (`EXPIREAT`) は現行トークンの `exp` よりも 1 分長く設定し、トークンを差し替えるたびに更新する。現行トークンと同じく、TTL はガベージコレクションのための値である。この TTL は、Sorted Set 内の最大スコア、すなわち直近に追加したメンバー自身のスコアと常に同期させる。スコアそのものが `old_exp + 1分` というマージンを持つ理由は、次項の再利用検知における刈り取り (`ZREMRANGEBYSCORE`) と `ZSCORE` 照会が同一リクエスト内で連続して実行されるためである。提示されたトークンの `exp` 直前に処理が行われた場合、マージンが無ければ、照会対象のメンバー自身が刈り取りによって消えてしまい、再利用が検知されない事態になる。`EXPIREAT` は独自のマージンを持つのではなく、このスコアのマージンにそのまま追従する。スコアは各リフレッシュを経るごとに単調増加するため、「直近に追加したメンバーのスコア」は常に「現存する全メンバーの最大スコア」と一致し、`EXPIREAT` をそれに同期させておけば、それ以前に追加された (まだ刈り取られていない) メンバーの必要期限を下回ることはない。

#### 再利用検知
{/* MARK: Reviewed Above */}

`POST /refresh` において、提示されたリフレッシュトークンが `rt:{sub}:{sid}` と一致しない場合、次の手順で、再利用検知を行う:

1.  スコア (元のリフレッシュトークンの `exp` + 1m) が現在時刻以前のエントリを刈り取る。

    ~~~redis
    ZREMRANGEBYSCORE rt_spent:{sub}:{sid} 0 <現在時刻>
    ~~~

2.  提示トークンのハッシュがこの Sorted Set に含まれるかどうかを調べる。

    ~~~redis
    ZSCORE rt_spent:{sub}:{sid} <presented_rt_hash>
    ~~~

3.  `ZSCORE` が値を返した場合、その RT は**有効期限内かつ使用済み**であり、再利用が検知されたことを意味する。この場合は、`rt:{sub}:{sid}` と `rt_spent:{sub}:{sid}` を即座に削除し、セッションを強制終了する。

    ~~~redis
    MULTI
    DEL rt:{sub}:{sid}
    DEL rt_spent:{sub}:{sid}
    EXEC
    ~~~

4.  `ZSCORE` が NULL を返した場合、その RT は「未知の RT」または「既に期限切れで刈り取られた RT」である。セッションは終了させず、当該リクエストだけを `403 Forbidden` で拒否する。

この判定順序により、**有効期限内の使用済み RT のみ**が再利用として扱われる。既に `exp` を過ぎた RT は再利用ではなく単なる期限切れであり、セッション侵害の証跡には用いない。

## 8. 監査ログ

認証サービスは、GDPR 第 5 条 2 項 (説明責任) および第 32 条 (処理のセキュリティ) に基づき、以下のイベントを記録する。監査ログは改竄検知可能な append-only ストリームとして保持し、タイムスタンプは UTC で記録する。

### 8.1 記録対象イベント

| イベント                      | 記録フィールド                                    | 備考                                                      |
| ----------------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| パスキー登録                  | `sub`・タイムスタンプ                             | `POST /attestation/result` 成功時。認証ではなく登録の記録 |
| パスキー失効                  | `sub`・`credential_id`・タイムスタンプ            | `POST /passkeys/revoke` 成功時                            |
| 認証成功                      | `sub`・`sid`・タイムスタンプ                      |                                                           |
| 認証失敗                      | IP アドレス・タイムスタンプ・失敗理由             |                                                           |
| 凍結中の認証試行              | `sub`・タイムスタンプ                             |                                                           |
| セッション失効                | `sub`・`sid`・タイムスタンプ                      | `POST /revoke` で実際に `rt:{sub}:{sid}` を削除した場合のみ。自然失効および no-op の場合は記録しない |
| RT 再利用検知                 | `sub`・`sid`・提示 RT ハッシュ・タイムスタンプ    | セッション強制終了を伴う                                  |
| AT/RCAT と RT の sub が不一致 | AT/RCAT の sub・RT の sub・`sid`・タイムスタンプ  | `POST /refresh` は 401、`POST /revoke` は 200             |
| RT 署名検証失敗               | IP アドレス・失敗理由・タイムスタンプ             |                                                           |
| RT 不正 (`typ` 不一致・期限切れ・未知の `sid` 等) | `sub`・失敗理由・タイムスタンプ       |                                                           |
| リカバリーコード使用          | `sub`・成否・タイムスタンプ                       |                                                           |
| リカバリーコード再発行        | `sub`・タイムスタンプ                             | `POST /recoveryCodes/reissue` 成功時                      |
| レート制限超過                | `sub`・タイムスタンプ                             |                                                           |
| 鍵ローテーション実行          | 旧 `kid`・新 `kid`・タイムスタンプ                | 構成変更の監査用                                          |

### 8.2 IP アドレスの記録について

IP アドレスは GDPR 上の個人データに該当する。本仕様では、`sub` が特定できない場合に限り、認証主体の代替情報として IP アドレスを記録する。IP アドレスの記録に関する法的根拠・保存期間・削除ポリシーについては別途規定する。
